# ADR-016 Place Search Data Licensing — 저장 가능한 장소 데이터로의 전환

Date: 2026-10-25
Status: Accepted (2026-10-28) — 카카오 측 데브톡 답변으로 Option C(사용자 확정 핀) 불허 확인 → **Option D′(공공데이터 정본 + 카카오 매칭)** 채택. 설계: [[Place Matching]]

> 법률 자문이 아니다. 아래 "확인 결과"는 2026-10-25 시점에 직접 연 공식 문서와, 원문을 직접 열 수 없었던 부분은 2차 자료로 구분해 적었다.
> 출시 전 반드시 각 공급자에 공식 질의해 회신을 이 문서에 기록한다.

---

## Context

Couple Map 의 핵심 데이터는 **사용자가 보드에 담은 장소**다. 현재 구조는 다음과 같다.

```text
App → Edge Function(place-search) → 외부 지역 검색 API
  → 결과(이름·주소·좌표) 중 사용자가 고른 1건을 public.places 에 영구 저장
  → 이후 지도 핀·동선·반응·메모·푸시 알림 본문에 계속 재사용
```

> **정정(2026-10-25 스파이크 중 확인):** 레포의 `supabase/functions/place-search` 는 네이버를 호출하지만,
> **실제 배포된 함수는 카카오 로컬을 호출한다**(응답 `provider: "kakao"`, `providerPlaceId` = 카카오 장소 ID).
> 운영 DB `places` 11건도 전부 `provider = 'kakao'` 이고, 운영 CHECK 제약은 `('kakao','naver','manual')` 이다(레포 0001 은 `('naver','manual')`).
> 즉 지금 운영에서 실제로 걸리는 것은 **카카오 운영정책**이고, 레포 코드·마이그레이션은 운영과 어긋나 있다(드리프트).

즉 **외부 검색 API 의 결과 데이터(이름·좌표)를 우리 DB 에 영구 보관하고 재사용**한다.
상업 출시(구독·스티커 판매)를 앞두고, 검색 공급자 약관이 이 구조를 허용하는지 확인할 필요가 생겼다.
또 지도는 이미 MapLibre + OpenFreeMap 으로 옮겨서(ADR-013), "지도·검색을 카카오로 통일"한다는 ADR-006 의 전제가 사라졌다.

### 1. 네이버 (지역 검색)

| 항목 | 내용 | 근거 |
|---|---|---|
| 결과 데이터 저장 | 회사 사전 동의 없이 결과 데이터를 허용 범위를 넘어 "복제, 저장, 가공, 배포"하는 것을 금지 | **원문 확인** — 네이버 클라우드 플랫폼 AI·Naver API 서비스 이용약관 제5조 ⑧ (v6.0, 2025-03-20 적용) |
| 출처 표시 | 결과 데이터에 회사 로고·지정 표시 게재를 요청할 수 있고 고객은 준수 | **원문 확인** — 같은 약관 제5조 ⑨ |
| (참고) Maps API | 결과는 "받은 즉시 1회" 사용만 허용, 별도 저장·DB화·재사용 금지 | **원문 확인** — 같은 약관 부가 조항 Maps API (2) |
| 검색 API 특약 | 검색 데이터(가공·파생물 포함)의 복사·저장·캐싱 금지. 예외는 서버 이력 조회 최대 21일, 기기 24시간/새 질의 시까지. 결과 페이지 광고·API 수익화 금지 | **2차 자료** — NAVER API HUB 검색 API 개별 특약 2.1~2.4(2026-09-07/09-20 시행)를 인용한 개발자 이슈·블로그. 특약 원문은 콘솔 동의 화면에서만 보이며 developers.naver.com 은 이 환경에서 접근 불가 |
| 제공 방식 변경 | 개발자센터 신규 신청 종료 2026-07-31, 기존 방식 지원 종료 **2027-06-30**, 이후 NAVER API HUB(현재 한시 무료, 유료화 공지 예정) | **2차 자료** — 이관 가이드 블로그 다수 일치. NAVER API HUB 서비스 이용약관 개정 공지(시행 2026-10-07)는 원문 확인 |

→ **판단:** 사용자가 고른 장소의 이름·좌표를 영구 저장하는 현재 구조는 일반 약관(제5조 ⑧)만으로도 위반 소지가 크고,
2차 자료의 검색 특약(저장·캐싱 금지, 21일/24시간 예외)이 맞다면 명백히 허용 범위 밖이다. 수익화 금지 조항도 구독 도입과 충돌할 수 있다.

### 2. 카카오 (로컬 API — 키워드 장소 검색)

| 항목 | 내용 | 근거 |
|---|---|---|
| 캐시 | "사용자 환경을 개선하기 위한 목적 외" 캐시, 또는 캐시 후 최신 데이터로 유지하지 않는 행위 금지 | **원문 확인** — Kakao Developers 운영정책 제5조 제20호 (2026-04-20 적용) |
| 복제·제공 | 카카오 사전 승낙 없이 얻은 정보를 복사·복제·변경하거나 타인에게 제공하는 행위 금지 | **원문 확인** — 같은 운영정책 제5조 제30호 |
| 상업적 이용 | "허가되지 않은 상업적 목적으로" 판매·재판매·악용 금지(일반 상업 서비스 사용 자체는 금지하지 않음) | **원문 확인** — 같은 운영정책 제5조 제11호 |
| 장소 저장 범위 | 장소 ID·URL 은 카카오맵 연결 용도로 보관 가능. 세션 동안 일시 유지 후 폐기는 가능. 저장한 장소 정보를 앱 재실행 때 불러와 쓰는 형태는 불가 | **카카오 측 데브톡 답변**(2026-10-23, 답변자 C.L) |
| 타사 지도 위 표시 | 다른 지도 API 와 조합 사용은 제한하지 않음(카카오맵 SDK 권장). 응답 결과를 저장해 반복 사용하는 것은 불허 | **카카오 측 데브톡 답변**(2026-08-18, 답변자 C.L) |
| 쿼터 | 키워드·카테고리 장소 검색 각 일 10만 건 무료(개발자 계정의 첫 앱), 월 합산 300만 건. 추가 쿼터 건당 2원 | **원문 확인** — 쿼터 문서 |

→ **판단:** 카카오로 바꿔도 **이름·좌표 영구 저장은 불가**하다. 저장 가능한 것은 장소 ID·URL 뿐이고,
ID 로 상세를 다시 조회하는 공개 API 도 없어 "ID 만 저장하고 매번 다시 조회" 방식도 성립하지 않는다.
ADR-006(카카오 통합)만으로는 문제가 해결되지 않는다.

#### 2-1. 우리 구조와 같은 질문에 대한 카카오 측 답변 (2026-10-28 조사)

다른 개발자들이 Option C 와 거의 같은 구조를 이미 물었다. 답변자는 모두 데브톡 카카오맵 API 게시판의 카카오 측 "Map".

| 질문한 구조 | 답변 | 근거 |
|---|---|---|
| 카카오 지도 SDK + 로컬 검색. 검색 좌표는 지도 이동에만 쓰고, 사용자가 핀을 놓아 확정한 좌표를 저장(핀을 안 움직인 경우 포함) | **불가** — "로컬 API 검색 결과를 기반으로 한 좌표는 사용자가 화면에서 확인하거나 확정하는 절차를 거치더라도 별도로 저장하여 활용할 수 없습니다." 저장 없이 **표시할 때마다 실시간 호출**은 허용. SDK POI 라벨 이름 저장도 불가 | 2026-08-24, [151294](https://devtalk.kakao.com/t/sdk-poi/151294) |
| 카카오 지도 JS SDK. 로컬 검색으로 대략 위치 → 지도를 끌어 가운데 핀 맞춤 → **사용자가 쓴 이름** + 핀 좌표 저장 | **좌표 저장 불가** — "지정 좌표의 DB 저장 및 활용은 불가합니다." 검색 결과로 **지도를 옮기는 것만은 문제없음** | 2026-09-27, [151842](https://devtalk.kakao.com/t/topic/151842) |
| 초대제 맛집 기록 서비스(친구끼리 함께 간 곳 기록). 사용자가 고른 1건의 장소 ID + 장소명 저장 | **불가** — "로컬 API에서 제공하는 장소명은 저장하여 활용할 수 없으며 실시간 호출로만 이용 가능합니다." (질문자가 대안으로 낸 "사용자가 직접 쓴 이름만 저장"엔 답 없음) | 2026-10-19, [152223](https://devtalk.kakao.com/t/1-id/152223) |
| 로컬 결과는 화면 표시 + **공공데이터 매칭 조회 키**로만 쓰고 저장은 공공데이터 레코드만. 매칭 실패면 저장 거부. 카카오 응답은 메모리에서 버리고 로그 안 남김 | **허용** — "설명해 주신 일회성 조회로 활용 및 사용자 직접 입력 구조(API 호출 결과값이 아닌)는 허용됩니다." 장소 ID 는 단독 저장 가능, "장소명, 주소 등의 응답값을 함께 저장하여 활용하는 형태는 허용되지 않습니다." | 2026-09-16, [151647](https://devtalk.kakao.com/t/api/151647) |
| 자체 보유 공공데이터 55만 건에 카카오 장소 ID·place_url 만 매칭해 저장(운영자 일괄 매칭) | ID·URL 저장 **허용**. 일괄 매칭은 "로컬 API 실시간 호출 정책에 위배되는 것으로 보이지는 않습니다" + 구조 상세 설명 요청(확답 아님) | 2026-08-26, [151335](https://devtalk.kakao.com/t/db-id/151335) |

→ **판단:** Option C 는 회색 지대가 아니라 **카카오 측 답변상 불허**다(좌표·이름 모두). 사용자가 확정해도, 사용자가 이름을 직접 써도 좌표가 검색 결과에서 출발하면 안 된다.
허용 범위는 ① 검색 결과 화면 표시·지도 이동, ② 공공데이터 등 **우리 데이터를 찾는 일회성 조회 키**, ③ 장소 ID(+URL) 단독 저장, ④ 저장 없이 표시할 때마다 실시간 호출, ⑤ API 결과가 아닌 사용자 직접 입력이다.
(151842 는 카카오 지도 SDK 위에서 찍은 좌표라 우리(MapLibre) 경우와 조금 다르지만, 151294 의 "검색 결과를 기반으로 한 좌표" 기준은 지도 종류와 무관하게 읽힌다.)

## Options Considered

### Option A — 현행 유지 (네이버 결과 이름·좌표 영구 저장)

장점: 추가 작업 없음, 검색 품질 좋음.
단점: 약관 위반 소지(제5조 ⑧, 검색 특약). 2027-06-30 이후 HUB 이관·유료화 가능. 수익화 금지 조항과 충돌 가능. **출시 불가 수준의 리스크.**

### Option B — 카카오 로컬로 교체 + 결과 영구 저장 (ADR-006 그대로)

장점: 검색 품질 좋음, 무료 쿼터 넉넉.
단점: 운영정책 제5조 제20·30호와 카카오 측 답변상 저장 불가. A 와 같은 문제를 공급자만 바꿔 반복.

### Option C — 외부 검색은 "찾기"에만, 저장은 사용자 확정 핀

검색 결과(카카오/네이버)는 화면 표시용으로만 쓰고 세션이 끝나면 버린다. 사용자가 결과를 고르면 지도가 그 위치로 이동하고,
**사용자가 핀 위치와 이름을 확정**한 것만 저장한다. 카카오라면 장소 ID·URL 을 "카카오맵에서 보기" 링크용으로 함께 저장한다.

장점: 현재 UX 를 거의 유지. 구현 작게 시작 가능.
단점: 확정된 좌표·이름이 결국 검색 결과에서 왔다면 "결과의 저장"으로 볼 여지가 남는다(**회색 지대 — 공식 질의 필요**).
사용자가 이름을 직접 다듬는 단계가 늘어난다.
→ **2026-10-28: 카카오 측 답변상 불허 확인**(위 2-1 — 151294·151842·152223). 철회.

### Option D — 공공데이터 기반 자체 장소 인덱스 ★권장(1차 검색원)

상가(상권)정보 CSV 를 분기마다 Supabase 에 적재하고(pg_trgm 키워드 + 지도 중심 거리 정렬), 우리 DB 에서 직접 검색한다.
저장되는 장소는 **우리가 이용 권리를 가진 데이터**다.

장점: 저장·상업 이용 제한 없음. 쿼터·요금·공급자 종속 없음. 결과 수 제한 없음(현재 네이버는 5건).
단점: 상가업소 위주라 공원·관광지·랜드마크가 빠진다. 분기 갱신이라 신규 가게 반영이 늦다. 상호 표기가 사용자가 아는 이름과 다를 수 있다.
전국 적재 시 수백만 건(정확한 건수는 적재 시 확인) → 무료 플랜(500MB) 초과, Pro 필요.

### Option D′ — 공공데이터 정본 + 카카오 매칭 ★채택(2026-10-28)

카카오 검색은 **찾기(화면 표시)와 매칭 조회 키**로만 쓰고, 저장은 **공공데이터 레코드 + 카카오 장소 ID(카카오맵 링크)** 만 한다.
사용자가 카카오 결과를 고르면 서버가 그 자리 주변의 공공데이터에서 같은 가게를 찾아, 그 레코드의 이름·좌표로 핀을 만든다.
매칭이 안 되면 사용자 핀(우리 데이터로 동네까지만 이동 → 사용자가 직접 찍고 이름을 씀)으로 넘어간다.

장점: 검색 품질은 카카오 그대로(90%), 저장 데이터는 우리가 권리를 가진 것뿐. 카카오 측이 허용한 구조(151647·151335)와 같다. 공공데이터만 쓸 때(67%)의 랭킹 문제가 사라진다 — 랭킹은 카카오가, 정본은 공공데이터가 맡는다.
단점: 공공데이터에 없는 곳(랜드마크·영화관·팝업·최신 개업, 영업 중 가게의 약 18%)은 사용자 핀으로 떨어진다. 등록 상호가 사용자가 아는 이름과 다를 수 있다("어니언" → "어니언컴퍼니 성수점"). 적재·분기 갱신 파이프라인이 필요하다.

### Option E — Overture / Foursquare OS Places

장점: 라이선스상 저장·상업 가능, 글로벌.
단점: 한국 커버리지·한글 이름 품질 미확인. 데이터가 커서 지역 추출·적재 파이프라인 필요. D 의 보완 후보로 스파이크만.

### Option F — Google Places

장점: 품질.
단점: 결과를 지도에 띄우려면 Google 지도 필수 → MapLibre(ADR-013)와 충돌. 장소 ID 외 저장 금지. 제외.

## Decision (Accepted 2026-10-28)

1. **검색 결과를 정본으로 영구 저장하는 현행 구조(A)를 출시 전까지 중단한다.** B(카카오로 교체 후 저장)도 채택하지 않는다.
2. **저장 가능한 장소 = 우리가 권리를 가진 데이터만** 으로 한정한다.
   - (a) **공공데이터 레코드**(상가정보 — 카카오 결과로 찾아 매칭하거나, 나중에 자체 검색으로 고른 것)
   - (b) **사용자가 직접 만든 핀**(우리 지도에서 직접 찍고 이름을 직접 붙인 장소 — 좌표가 카카오 결과에서 출발하지 않는다)
3. 카카오 검색은 **D′ — 찾기(화면 표시·지도 이동) + 공공데이터 매칭 조회 키**로만 쓴다. 카카오 응답은 요청 안에서 쓰고 버린다(저장·로그·캐시 없음, 앱은 메모리 표시만).
   카카오에서 저장하는 것은 **장소 ID 단독**(카카오맵 링크용)뿐이다.
4. ~~C(사용자 확정 핀)~~ 는 카카오 측 답변상 불허라 철회한다(2-1). 2026-10-28 구현분은 D′ 로 교체한다.
5. 매칭이 안 되는 곳(랜드마크·팝업·신규 개업)은 (b) 사용자 핀으로 받고, 보완원(OSM 랜드마크·큐레이션 목록)은 다음 단계에서 붙인다.

(원래 4번 "D 채택은 스파이크 게이트로 결정" — 게이트는 D 단독 검색 기준이었고 미달(67%). D′ 는 검색을 카카오가 맡으므로 게이트 대상이 아니라 **매칭률**로 본다 — [[Place Matching]] §검증.)

### 스파이크 게이트 (1~2일)

- 서울 상가(상권)정보만 적재 → 실제 데이트 검색어 30개(카페·식당·브랜드명·동네명)로 네이버 결과와 비교

## 스파이크 결과 (2026-10-25)

방법: 상가(상권)정보 2026-06-30 기준 **서울 554,092건**을 로컬에 올려 시제품 검색(`scripts/place-search-spike`)으로 30개 검색어를 돌리고,
같은 검색어를 **현재 배포된 place-search(카카오)** 에 보내 비교했다. 카카오 결과는 판정에만 쓰고 저장하지 않았다.

- v1 = 데이터 필드만 / v2 = + 동네 별칭(홍대→서교동 등) / v3 = + 드문 단어 가중치 + 합성어 분리("한옥카페"→한옥+카페)
- 판정: 이름 검색은 상위 5건 안에 기대 장소(이름+시군구), 카테고리 검색은 상위 5건 중 3건 이상 해당 업종+지역

| 구분 | v1 | v2 | **v3** | 카카오 |
|---|---|---|---|---|
| 이름 검색 (20) | 15 | 15 | **16** | 17 |
| 랜드마크 (4: 서울숲·뚝섬한강공원·남산서울타워·롯데월드) | 0 | 0 | **0** | 4 |
| 카테고리+지역 (6) | 3 | 3 | **4** | 6* |
| **합계 (30)** | 18 | 18 | **20 (67%)** | 27 (90%) |

\* 배포 함수 응답엔 업종이 없어 카카오 카테고리는 지역 일치만 셌다(관대한 판정).

**게이트 결과: 미달** — 공공데이터 단독 67% < 80%. (지연 시간은 시제품이 인덱스 없는 파이썬 선형 탐색이라 측정 무의미 — Postgres pg_trgm 에서 별도 측정 필요)

실패 원인 분해:

1. **데이터에 아예 없음(커버리지)** — 이름 검색 20개 중 3개(누데이크 신사, 커피한약방, CGV 용산아이파크몰). 업종 247개 중 **영화관 분류가 없다**.
   "노티드 청담"은 청담 지점이 없고 삼성 지점만 있어 v3 에서 다른 지점으로 걸렸다(엄밀히는 실패).
2. **장소 종류 자체가 없음** — 공원·전망대·테마파크 같은 **랜드마크는 상가업소가 아니라 0/4**. 이름이 붙은 주변 가게("스타벅스 뚝섬한강공원")만 나온다. 카카오는 4/4 모두 장소 자체를 찾았다.
3. **업종 분류가 거칠다** — "와인바"·"한옥카페" 같은 데이트 수요 단위가 업종에 없다. v3 의 합성어 분리로 일부 개선(와인 0→4, 한옥카페 0→2)했지만 "어바웃와인합정(김밥/만두/분식)" 같은 오탐이 섞인다.
4. **잘 되는 것** — 데이터에 있는 가게는 랭킹이 거의 다 맞췄다(데이터에 있는 17개 중 15~16개 1~2위). 카카오가 0건을 낸 검색어 2개(툭툭누들타이 연남, 할아버지공장 성수)는 공공데이터가 1위로 찾았다.

**해석:** 공공데이터는 "동네 가게"에는 쓸 만하지만 데이트 검색의 큰 축인 **랜드마크·문화시설(공원·전망대·영화관·전시)** 과 **최신 핫플**이 비어 있어 단독 1차 검색원으로는 부족하다.
카카오가 품질에서 확실히 앞서므로, **카카오 "찾기 보조 + 사용자 확정 핀"(Option C)의 공식 허용 여부가 결정의 핵심 변수**가 됐다.

다음 판단 순서:

1. 카카오 공식 회신에서 C 가 허용되면 → **C 를 1차**, 공공데이터는 저장 가능한 정본·오프라인 보완으로.
2. C 가 불허되면 → 공공데이터 + **랜드마크 보완원**(한국관광공사 TourAPI 관광지·문화시설 — 이용허락 확인 필요, 또는 Overture Places 한국 커버리지 스파이크) + **사용자 핀**. 품질 저하를 감수한다.

→ **2026-10-28: 2번으로 확정**(카카오 측 답변 2-1). 다만 검색까지 공공데이터로 바꾸지 않고 카카오를 찾기·매칭 키로 남겨(D′) 검색 품질 저하는 피한다.

## 시드 파일럿 결과 (2026-10-25)

방법: 웹 리서치로 성수·연남·익선(+북촌·삼청 인접) 데이트 장소 **100곳**(가게 91, 팝업·전시 공간 4, 랜드마크 5)을 뽑았다.
저장한 것은 **사실만**(이름·동네·종류·출처 URL — `scripts/place-search-spike/pilot_seed.json`)이고, 리뷰·사진·평점은 가져오지 않았다.
이를 상가정보(서울)와 매칭(`pilot_match.py`)한 뒤 오매칭을 수동으로 걸러냈다.
공공데이터에서 놓친 곳은 배포된 카카오 검색으로 지금도 있는지만 확인했다(판정만 남김).

| 분류 | 공공데이터에 있음(수동 확인) | 공공데이터엔 없지만 카카오엔 있음 | 둘 다 확인 안 됨(폐업·이전 추정) |
|---|---|---|---|
| 가게 91 | **45** | 10 | 36 |
| 팝업·전시 공간 4 | 1 (라인프렌즈 스퀘어) | 3 | 0 |
| 랜드마크 5 | **0** | (미확인) | — |

- **지금 영업 중인 가게 기준 공공데이터 커버리지 ≈ 82%** (45 / 45+10). 가게만 놓고 보면 게이트(80%)를 넘는다.
- **웹 리스트는 빨리 낡는다:** 시드의 36%를 지금도 있는지 확인하지 못했다. 출처 리스트가 2021~2024년 글이 많았기 때문이다.
  공공데이터는 분기마다 "영업 중" 상가만 담아서, 오히려 **폐업 걸러내기**에 쓸 수 있다.
  (배포된 카카오 검색이 실존 장소에도 0건을 낸 적이 있어 "둘 다 없음"엔 일부 실존 장소가 섞였을 수 있다.)
- **랜드마크 0/5, 팝업 1/4:** 자동 매칭에 걸린 건 전부 이름을 딴 주변 가게("서울숲점", "연트럴파크점", "서순라길점")였다.
  공원·길·유적은 공공데이터에 없고, 팝업은 기간이 짧아 상가로 잡히지 않는다.
- **등록명이 다르다:** 어니언→"어니언컴퍼니 성수점", 대림창고→"성수동대림창고갤러리", 마가렛→"카페마가렛", 툭툭누들타이→"툭툭누들타이주".
  업종도 칵테일 바가 "경양식", 카페 겸 바가 "요리 주점"으로 잡혀 있다 → 별칭·퍼지 매칭과 **우리 자체 태그**가 필요하다.
- **짧은 이름은 오매칭이 잦다:** 하하→"하하하우스(펜션)", 귀→"귀빈", 옥타→"옥타즈(사진관)", 아르크→"아르크주(광고 대행)" → 두 글자 이하 상호는 사람 확인이 필요하다.

**결론(30개 검색어 스파이크와 종합):** 공공데이터는 **실존 가게의 정본**으로는 충분하다(약 82%).
비는 곳은 **랜드마크·전시·팝업**과 **최신 개업**이다. 다음 구성으로 메우는 안이 현실적이다.

1. **가게** = 공공데이터 정본(분기 갱신으로 폐업도 정리) + 별칭 사전
2. **랜드마크·문화시설** = 우리가 사실만 모아 만드는 큐레이션 목록(수백 건 규모, 출처 URL 보관) + 공원 등 공공데이터 보완
3. **팝업·신규 개업** = 사용자 핀(짧은 수명, 사용자가 만든 데이터)
4. **외부 검색(카카오)** = 공식 허용 범위 안에서 "찾기 보조"만

### 해외 확장 시사점

- **지도는 이미 해외 대응이 끝나 있다:** MapLibre + OpenFreeMap 은 전 세계 타일이라 지도 API 를 바꿀 필요가 없다.
- **장소 검색의 저장 제약은 해외 상용 API 도 같다:**
  - Google Places: 장소 ID 만 저장 가능, 지도는 Google 지도여야 함
  - Mapbox: 영구(permanent) 지오코딩은 저장할 수 있지만 Mapbox 지도와 함께 써야 함
  - Foursquare Places API: fsq_id 만 무제한 캐시, 나머지는 서버 저장 불가
  → "해외 API 로 갈아끼우면 끝"은 아니다.
- **해외에선 깨끗한 경로가 더 쉽다:** Overture Places(약 8,800만 건, CDLA/Apache)·Foursquare OS Places(Apache 2.0)·OSM 은 저장·상업 이용이 가능하다.
  미국·유럽·일본 커버리지가 한국보다 나을 가능성이 커서, 이 ADR 의 "저장 가능한 정본" 구조를 그대로 옮기기 좋다(국가별 스파이크로 확인 필요).
- 따라서 지금 할 일은 **장소 모델을 공급자 중립으로** 두는 것이다(`provider` + `provider_place_id` + 우리 정본 ID). 국가가 바뀌면 정본 공급원만 바꾼다.

| (비교) 서울 성수 | 3,619 | — | 이름 77% 가 한글 |

- **가게·맛집은 잘 있다:** 이치란·츠지한·블루보틀·후글렌·쿠쿠루·리쿠로 오지상·팁싸마이 등 현지 이름(일본어·태국어·영어)으로 대부분 찾힌다.
- **한글로는 하나도 안 찾힌다:** 해외 장소에 한국어 이름이 없다. 한국 사용자가 "이치란"을 쳐도 못 찾는다 → 해외 검색엔 한글 별칭(번역·음역)이나 별도 검색 수단이 필수.
- **큰 시설은 "안의 가게"만 있는 경우가 있다:** 시부야 스카이·구로몬 시장·아이콘시암 — 국내 상가정보의 랜드마크 문제와 같은 모양.
- **업종 표기가 지저분하다:** 메이지 신궁 = christian_place_of_worship, 아베노 하루카스 = atm, 시암 파라곤 = pharmacy. 같은 이름·같은 자리 중복 약 0.25%. 영업 상태(`operating_status`)는 거의 비어 있어 폐업 여부를 알 수 없다.
- **한국은 약하다:** 성수 같은 구역에서 Overture 3,619건 vs 상가정보(데이트 업종만) 6,318건 → 국내 정본은 상가정보 유지.
- 크기: 도쿄 도심만 parquet 14MB — 여행지 도시 몇 곳을 우리 DB 에 넣는 건 가볍다.

→ **판단:** 해외 정본 데이터로 Overture(+Foursquare)는 쓸 만하다. 막히는 건 데이터가 아니라 **한글 검색**이다.
선택지: ① 인기 장소부터 한글 이름(음역·번역)을 미리 만들어 별칭으로 붙인다(우리가 만든 데이터라 저장 가능), ② 국내 카카오처럼 다른 검색 API 를 "찾기·매칭 조회 키"로만 쓰고 저장은 Overture 레코드로(후보: Amazon Location `SingleUse` — 지도 제약·저장 조건 확인 필요), ③ 사용자가 붙인 이름을 별칭으로 쌓는다. 처음엔 직접 핀 + 현지·영어 이름 검색으로 시작해도 된다.

## Rationale

- 두 공급자 모두 **결과 데이터의 영구 저장**을 막는다(네이버 제5조 ⑧ 원문, 카카오 운영정책 제5조 제20·30호 원문 + 카카오 측 답변). 공급자를 바꾸는 것으로는 해결되지 않고, **저장하는 데이터의 출처**를 바꿔야 한다.
- Couple Map 의 가치는 "장소에 쌓이는 대화"(ADR-014)다. 대화가 매달릴 장소가 공급자 약관에 묶여 있으면, 출시 후 언제든 데이터를 지워야 할 수 있다 — 제품의 핵심 자산이 남의 약관에 달려 있게 된다.
- 공공데이터는 "이용허락범위 제한 없음"이라 구독·스티커 판매 같은 수익화(ADR-013 Product Philosophy 방향)와도 충돌하지 않는다.
- 사용자 핀(b)은 원래부터 사용자가 만든 데이터라 어떤 공급자 약관에도 걸리지 않는 최후의 안전망이다.

## Consequences

좋은 점

- 출시 후 약관 문제로 장소 데이터를 지워야 하는 리스크 제거.
- 검색 결과 수 제한(네이버 5건)과 2027-06-30 이관 일정에서 자유로워짐.
- 검색 비용·쿼터가 사실상 0(DB 비용에 포함).

나쁜 점

- 초기 구현량 증가: 적재 스크립트, 분기 갱신, 검색 RPC, 검색 UI 의 "직접 핀 찍기" 경로.
- 상가 외 장소(공원·관광지)와 신규 가게는 품질이 떨어질 수 있음 → 사용자 핀으로 메워야 함.
- 전국 적재 시 Supabase Pro 가 사실상 필수(어차피 출시 시 필요).

향후 영향

- `places.provider` 값 체계 변경: `'public' | 'user' | 'kakao'`(+ 기존 `'naver'` 레거시). `provider_place_id` 는 공공데이터 키 또는 카카오 장소 ID, 카카오맵 URL 컬럼 추가 검토.
  운영 DB 에 레포에 없는 `places.provider` 제약 변경(카카오 추가로 보이는 저장 쿼리)이 있어 마이그레이션 전에 실제 제약을 대조한다.
- 기존 네이버 유래 장소(운영 DB 11건)는 공공데이터와 매칭되면 재연결, 아니면 사용자 확인을 거쳐 사용자 핀으로 전환한다.
- 푸시 알림 본문(0006)은 저장된 `places.name` 을 쓰므로, 데이터 출처가 바뀌어도 그대로 동작한다.
- 외부 리뷰 신호(예: 네이버 지도 리뷰의 "누구랑 갔나요 → 연인") 는 API 가 없고 저장도 금지라 쓸 수 없다.
  대신 Couple Map 자체가 같은 신호를 만든다 — 커플들이 보드에 담고 ❤️ 를 단 장소의 **익명 집계**("커플들이 많이 담은 곳")를
  사용자 장소(정본)에 붙여 검색 랭킹·추천에 쓸 수 있다(개인정보처리방침 고지·최소 집계 단위 필요). 우리가 권리를 가진 데이터라 이 ADR 의 원칙과 맞는다.
- ADR-006(카카오 통합)은 이 ADR 로 **Superseded** 표기했다(2026-10-29).

## 결정 보강 — 하이브리드 + 카카오 실시간 핀 (2026-10-29)

- 공방·소품샵은 공공데이터로 4분의 1만 잡혀(실측 — [[Place Matching]] §11) "매칭 없음 → 직접 찍기"의 수고가 크다.
- **결정:** 공공데이터와 맞으면 지금처럼 공공 레코드로 저장하고, 맞지 않으면 **카카오 실시간 핀** — 카카오 장소 ID·사용자가 친 검색어만 저장하고 볼 때마다 카카오에서 좌표·이름을 불러와 표시한다(데브톡 151294 "화면 노출 시점마다 실시간 호출 표시는 허용", 151647 "장소 ID 단독 저장 허용"). 앱은 온라인 전제라 오프라인 표시는 포기한다.
- **장소 데이터 구매는 수요가 커진 뒤.** 2026-10-29 조사: 저장 가능한 POI 파일은 국내(맵퍼스·아이나비·NICE지니데이타 등)·해외(Foursquare·HERE·TomTom 원본) 모두 견적 문의라 공개 가격이 없다. API 로 저장 가능한 건 AWS Amazon Location 의 `intendedUse=Stored`(단가 미확인, 한국 품질 미확인)와 주소 전용 Mapbox 영구 지오코딩(1,000건당 $5)뿐. Google 은 place_id 만 저장(보여 줄 때마다 Details 1,000건당 $5~). 카카오 로컬은 하루 10만 건 무료 뒤 건당 2원(2026-07-21 정책). 해외 확장의 출발점은 무료·저장 가능한 Overture·FSQ OS Places.
- `0016_place_kakao_live.sql` 적용(2026-10-29), place-search 에 `resolve` 추가 배포. 예전 provider `kakao`·`naver` 는 남은 행이 없어 제거.

## 구현 — Option C 우선 (2026-10-28) — **철회, D′ 로 교체**

> 같은 날 조사한 카카오 측 답변(2-1)으로 C 는 불허. 아래는 기록용이다. 교체 설계는 [[Place Matching]].
> 교체 전까지 이 빌드로 카카오 결과를 골라 저장하면 운영 DB 에 카카오 유래 이름·좌표가 쌓인다 → 테스트는 "직접 핀 찍기" 위주로.

카카오가 품질에서 앞서므로(90% vs 공공데이터 67%) **C(찾기 보조 + 사용자 확정 핀)** 를 먼저 구현하고, 카카오 공식 회신에서 허용되지 않으면 끄는 스위치를 둔다.

- **스위치:** `src/constants/config.ts` `KAKAO_SEARCH_ASSIST`(지금 true). false 면 검색 없이 "직접 핀 찍기"만 남는다.
- **검색 결과는 표시 전용:** React Query 메모리 캐시만(gcTime 5분, 디스크 저장 없음), 결과 목록에 "검색 제공: 카카오" 표기.
- **핀 확정:** 결과를 고르면 바로 저장하지 않고 지도가 그 자리로 이동 → 화면 가운데 고정 핀을 지도를 움직여 맞추고, 이름(카카오 이름으로 채워 두되 고칠 수 있음)을 확인해 "여기에 핀 꽂기". 저장 위치 = 확정 순간의 지도 가운데.
- **저장 범위:** 이름·좌표는 사용자가 확정한 값, `provider = 'kakao'`, `provider_place_id` = 카카오 장소 ID(카카오맵 링크용). 주소·전화·업종 등 다른 결과 필드는 저장하지 않는다.
- **카카오맵에서 보기:** 핀을 누르면 반응 바에 "카카오맵" 버튼 → `https://place.map.kakao.com/{id}`(영업시간·리뷰는 카카오맵에서).
- **직접 핀 찍기:** 검색 시트 아래 항상 표시(검색어가 있으면 이름 기본값). `provider = 'manual'`, 외부 데이터 0. (Action Item 3 의 "지도 길게 누르기" 대신 가운데 핀 방식)
- **태블릿:** 장소 찾기 화면(PlaceAdd)에서 고르면 지도로 돌아가 같은 확정 모드(`BoardDetail` 파라미터 `draft`).
- **DB:** `0013_place_provider_kakao.sql` — provider CHECK 를 이름과 무관하게 지우고 `('naver','manual','kakao')` 로 다시 만든다(운영 드리프트 기록).
- **남은 것:** 카카오 공식 질의(이 구조 그대로) · 배포된 `place-search`(카카오) 소스를 레포에 동기화(레포는 아직 네이버 코드) · 운영 카카오 유래 장소 11건 정리.
